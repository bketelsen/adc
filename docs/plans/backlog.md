## Execution-plan priorities

The execution-plan work below was prioritized by Brian after examining [core PR #135 / Plan 0007](https://github.com/frostyard/core/pull/135). The plan crosses repositories, reviewed code, releases, a single authorized canary, operational cutovers and a 48-hour observation window. Recording that sequence only in supervisor prose risks premature downstream work and repeated human continuation prompts. This backlog authorizes ADC development, not execution of the Frostyard migration.

1. **EP1 — Durable execution plans and dependency scheduling (first slice implemented).** Store versioned plans with stable step IDs, owners, completion criteria, source references and prerequisite edges. Dispatch eligible steps automatically within existing assignment authority; require current independent review before unlocking dependents; recover without duplicate runs; expose waiting reasons, evidence and transcript links. Why first: gives the supervisor a reliable memory of agreed work and keeps unaffected branches moving. Acceptance: a small R1→R2→(R3,R4) fixture survives interruption and correction, never starts a dependent early, and completes without human continuation. First slice uses reviewed ADC run completion; external milestones are EP2/EP3. Includes automatic designated review, quiescent-attempt recovery after upstream evidence changes, and a live plan view. See [execution plans](../design/execution-plans.md).
2. **EP2 — Explicit milestone requirements (typed evidence slice implemented).** Dependencies distinguish reviewed code, merged PR, published release, verified canary and human-supplied evidence; completion is tied to the requirement's evidence, not an agent's generic success message. Depends on EP1. Why: Repogen R1–R5 review is not proof that the production canary exists, and one canary is not permission to expand the closure. Acceptance: a code-review pass cannot satisfy a release/canary requirement; changing the evidence invalidates the affected gate. Implemented: typed step requirements, attempt-bound observation packets, human-only attestations, independent review pinning, withdrawal/replacement and dependent invalidation. Automatic external observation is EP3; structured per-check outcomes and integration environment evidence remain in the refinements below.
3. **EP3 — Durable external and timed waits (MCP/timer slice implemented).** Persist external references, observed versions, deadlines and reconciliation results; release worker slots while waiting, resume only relevant steps on verified change, recover missed events by reconciliation. Depends on EP1/EP2. Why: CI, merges, releases and observation periods should not consume an agent turn or need human nudges. Acceptance: a 48-hour gate also requires the specified real-publication event; restart or duplicate events cannot complete it twice or prematurely. Implemented: frozen generic MCP predicates, version/event/time conditions, durable leases and retries, bounded read-only polling, gateway re-admission, atomic evidence/wake, and live wait details. Conditions are sampled rather than continuous; webhook adapters and integration revalidation remain later work.
4. **EP4 — Repository and integration evidence ledger (implemented and qualified).** Record repository identity, base/output commits, PR/release references, the exact dependency versions consumed, and integration checks. Flag affected downstream validation when upstream evidence changes; coordinate overlapping work without requiring all repository work to serialize. Depends on EP1/EP2. Why: individually green PRs may never have been tested together, and local workspace paths are insufficient durable cross-repository provenance. Acceptance: the tested repository combination is inspectable; upstream change makes affected integration evidence stale without discarding unrelated work.
5. **EP5 — Step/artifact-bound operational approvals (implemented and qualified).** Bind approvals to a concrete action, target/environment, plan step and evidence revision, with a reviewable bundle and explicit invalidation when those change. Reuse existing capability/operation approvals and avoid approval for routine authorized corrections. Depends on EP2/EP4. Why: a draft-PR grant must not imply production publication, producer credential removal or image promotion. Acceptance: approval for the single canary cannot authorize a second publication or credential cutover.
6. **EP6 — Mediated GitHub delivery and execution preflight (implemented and qualified).** Provide narrowly scoped private fetch, push, draft-PR creation and read-only CI/PR/release inspection through the existing gateway; preflight required tools, runtimes, repository access and review portfolio before dispatch. Depends on existing protected execution; integrate with EP2/EP3/EP4. Why: protected workers can prepare public repository changes today but lack a qualified built-in authenticated delivery path; discovering missing tools after delegation wastes runs. Acceptance: protected reviewed commits reach a draft PR without worker credential exposure, permission escalation, duplicate publication or silent advisory fallback.
7. **Complete remaining permission/provider qualifications.** Protected Linux execution, provider tool controls, generic MCP gateway, scoped grants and bundled approval UI are implemented. See [the operating guide](../design/permissions.md) and [plan](permissions.md). EP6 covers authenticated repository delivery. HTTP MCP, external integrations, long-running recovery and exhausted-account behavior retain explicit qualification work. Existing organizations/schedules keep their settings.
8. **Separate-installation collaboration.** Supervisor-to-supervisor requests, with approval/execution in the receiving installation and a tracked external dependency stub for the requester. Build on EP2/EP3 so remote milestones have the same evidence/wait semantics as local work.

The plan UI belongs to EP1: show ready/running/review/waiting/blocked steps, exact prerequisites, evidence and links into runs on desktop and phone. Keep creation and revision conversational, with a human-readable workspace view; do not require people to author workflow files.

Remote execution, backup/export/restore and richer notifications remain later conveniences. No backlog item authorizes proposed infrastructure work or connection installation.

## Validation and review refinements

Added at Brian’s request after assessing the September 11, 2026 [software-factory article](https://www.firecrawl.dev/blog/ai-software-factory) against ADC’s plans and implementation. These refinements preserve the EP1–EP6 sequence and ADC’s general-purpose assignment model. Prioritize structured validation evidence within EP2/EP4, then the reviewer brief and visual evidence; address review-capacity controls and finding-quality measurement after those foundations. Environment preflight extends EP6. These are backlog requirements, not claims of implemented behavior.

1. **Structured validation evidence — extend EP2/EP4.** Record each required check’s command or verifier identity, outcome, artifact revision, relevant environment/dependency versions and supporting output. Distinguish observed results from agent-reported claims, and missing, failed, stale and inapplicable checks from passing ones. Run inexpensive deterministic checks before substantive model review and expensive integration checks where dependencies permit; diagnostics and correction must remain possible after failure. Why: current code evidence binds a path and commit, while check results are described in prose. Explicit records let ADC determine whether the required validation actually applies to the deliverable being accepted. Acceptance: missing, failed or stale required checks prevent readiness; material changes invalidate affected evidence; a restart preserves results and outstanding requirements. Keep verifier types extensible to documents and operational observations. [Spotify’s verification-loop design](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3) supports this ordering.
2. **Explicit reviewer briefs — build on existing independent review.** Assemble the authorized request, acceptance criteria, exact deliverable revision or changes, relevant authoritative sources and validation results for the reviewer. Require assessment of whether the result solves the requested problem, introduces unrelated changes or weakens checks to obtain a pass. Use the existing cross-family reviewer rather than adding a mandatory agent layer. Why: passing checks and a generic review verdict can miss scope drift or a technically valid result that fails the assignment’s purpose. Acceptance: qualification fixtures with unrelated changes, disabled checks and an unmet criterion receive concrete findings; ordinary authorized corrections continue automatically. This adapts [Spotify’s scope judge](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3) to ADC’s existing lifecycle.
3. **Visual and interaction evidence for UI deliverables — extend EP2/EP4.** Define affected flows from the changes and retain desktop/phone screenshots, interaction results and browser errors against the reviewed revision. Capture comparable before/after views when a baseline is available; identify unavailable baselines explicitly. Keep evidence in the assignment workspace and attach it externally only when publication is authorized. Why: ADC has browser qualification work, but a repeatable assignment requirement would catch layout and interaction failures that build/test success alone does not establish. Acceptance: a fixture with passing code checks but a broken phone flow cannot satisfy its UI requirement; screenshots and interaction results remain inspectable and become stale after relevant changes. Visual evidence supplements independent review.
4. **Review-capacity controls and outcome metrics — follow the evidence foundation.** Show work awaiting human review and its age; add configurable limits on starting additional maintenance when that queue exceeds the chosen capacity. Continue corrections, supervision and independent review, and preserve the priority of direct human requests. Measure time to accepted completion, correction rounds and human interventions alongside usage, with unavailable measurements explicitly unknown. Why: prioritizing reviewer model runs, which ADC already does, does not prevent finished work from overwhelming human review capacity. Acceptance: a configured backlog limit holds new maintenance while existing work can progress; resolving reviews releases eligible work without another prompt. This is an ADC scheduling proposal informed by the reviewer overload described in [Uber’s uReview account](https://www.uber.com/us/en/blog/ureview/).
5. **Individual findings and review-quality feedback — extend the review lifecycle.** Give findings stable IDs, evidence references, severity, resolution state and dismissal reasons while preserving their history across revisions. Consolidate duplicates and assess usefulness against observed corrections and human feedback; do not use a model’s self-reported confidence as the sole quality gate. Why: findings currently live in review text, making recurring objections, resolution and low-value repetition harder to track. Acceptance: each blocking finding has an inspectable disposition; a repeated finding retains its identity through correction; dismissal does not silently bypass required independent review. Evaluate quality on labelled fixtures and actual outcomes rather than comment volume. [Uber’s experience](https://www.uber.com/us/en/blog/ureview/) supports actionable findings, duplicate reduction and built-in feedback.
6. **Environment readiness and cleanup — extend EP6 preflight.** Check required runtimes/tools, repository access, worker/reviewer model availability, isolated test data and port allocation before dispatch. Record ownership and cleanup expectations for temporary environments while retaining durable assignment evidence. Keep credentials in mediated connections, outside workspaces. Why: separate worktrees alone do not resolve conflicting ports, shared databases or absent dependencies, and discovering these after delegation wastes runs. Acceptance: parallel qualification fixtures use separate test resources; unavailable prerequisites create specific recoverable waits or blockers without occupying model slots; cleanup preserves evidence and never removes another active run’s resources. Distinguish advisory checks from technically enforced execution boundaries.

Do not adopt the article’s secret-copying example, mandatory monorepo direction, automatic-merge defaults or a fixed two-CI-attempt handoff to humans. Preserve canonical-source references, existing publication authority and bounded supervisor reassessment with automatic authorized correction. No refinement requires Firecrawl or changes ADC into a GitHub-specific workflow engine.
