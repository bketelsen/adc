# Provider connections and execution

## Account selection

Each permanent role has an explicit provider and model. Existing records with no provider continue to mean Copilot. Category-default workers inherit their configured role's provider. Providers do not establish independence: OpenAI execution still requires a different model family for review. Codex supplies OpenAI models; Claude roles can use Copilot or the direct Claude provider. Direct Claude review, stdio MCP and local repository validation have passed with an explicitly connected account.

An assignment selects its accountable role's subscription and may explicitly select one additional subscription for a different provider. Both belong to the authorizing human. Delegation resolves a role's provider against that approved pair and pins the resulting account/provider on the run. It never searches other humans' portfolios or substitutes another provider/model. A missing matching subscription is an actionable delegation error. Each active run counts against the account actually executing it; usage attribution follows the same account. Reassignments revalidate the provider/funding pair, authority, required tool access and review family.

Recurring approval snapshots the same funding pair. A provider change that needs different funding requires a fresh proposal/approval. Account selection does not authorize broader scope or tools.

## Codex connection

The adapter uses the official [Codex app-server protocol](https://learn.chatgpt.com/docs/app-server), including managed ChatGPT device-code sign-in and experimental dynamic tools. The checked runtime is Codex CLI 0.153.0; protocol schemas are generated from that installed binary for compatibility checks. Set `ADC_CODEX_CLI_PATH` when `codex` is not on the service PATH.

Connections → + Codex creates an empty personal connection. Start ChatGPT sign-in, enter the displayed code at the official authentication page, and choose Check sign-in. Device-code authentication may need to be enabled on the ChatGPT account. The status page shows the signed-in identity and model catalog. Only the owning human can manage this sign-in. Changing authentication is rejected while that account has active ADC work.

Each account launches its own app-server with a private `CODEX_HOME` inside ADC's data directory. No host authentication or configuration is imported. OpenAI/Codex credential environment overrides are removed from the child process. Codex owns credential refresh and stores sign-in files in that private directory; ADC does not encrypt those provider-managed files with its own credential key. The directory must be protected and included in installation backups. Model conversations use ephemeral provider threads and ADC persists the authoritative assignment/run/artifact/evidence history.

## Execution and recovery

Codex receives ADC's existing tool declarations through dynamic tools. Calls execute the same durable handlers used by Copilot, retaining authority, organization, scope, decision and review checks. The adapter acknowledges a successful outcome tool before interrupting the provider turn. Provider exits or cancellation preserve unfinished work for ADC recovery. A provider turn that ends without an ADC outcome goes through the existing bounded continuation logic.

Only the current run's granted MCP connections are supplied, and they are marked required for startup. Provider-native collaboration, apps, plugins and host skill discovery are disabled for these clients. Ordinary execution uses the existing advisory authority posture and full host access; this is not an isolation guarantee. Proposal conversations receive only ADC proposal tools, no MCP connections or web search, shell tools disabled and a read-only Codex sandbox. That is a different provider configuration from Copilot's explicit tool allowlist; it has not yet received live model qualification. Unexpected native approval/input requests fail explicitly; human decisions belong in ADC tools.

Native command/file/MCP evidence and assistant messages are recorded with bounded redacted payloads. Usage notifications contain cumulative per-thread totals; ADC stores positive deltas, ignores repeated/out-of-order snapshots, and preserves missing fields as unknown. Requested models are checked against the account catalog and a differing thread-start model is rejected.

## Direct Claude provider

The direct provider uses the official Claude Agent SDK 0.3.268 with its bundled Claude Code 2.1.268 runtime through a small private Node bridge. Install the pinned dependencies with `npm ci --prefix runtime/claude --ignore-scripts`. Node 18+ is required; this installation uses Node 24.19.0. Set `ADC_CLAUDE_NODE` and `ADC_CLAUDE_RUNTIME_DIR` for deployment paths; `ADC_CLAUDE_CLI_PATH` optionally overrides the bundled native binary. The current path resolver is qualified on Linux x64; other platform packages and musl deployments need configuration and qualification.

Connections → + Claude creates a personal pending account. Its page supplies a copyable command that invokes Claude Code's own `auth login --claudeai` with a private `CLAUDE_CONFIG_DIR` under `providers/claude/<account-id>`. Run it as the ADC service user on the host, then choose Check sign-in. Only the owning human can view/manage this connection. ADC does not implement or embed a custom claude.ai OAuth flow, accept a subscription token, import desktop credentials, or fall back to API billing. Claude manages refresh and its own private credential files, which are not encrypted by ADC. Do not sign in over an existing account while its work is running; the application's disconnect action refuses active accounts. A host administrator's native CLI commands remain outside application controls.

Authentication research found conflicting official wording. The current [Claude support article](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan) says SDK, print mode and third-party app usage still draw from subscription limits and marks its earlier credit changes as paused. The [SDK overview](https://code.claude.com/docs/en/agent-sdk/overview) still restricts third-party products offering claude.ai login/rate limits without prior approval. ADC's implementation uses native personal CLI sign-in for this installation and the official SDK; it should not be represented as an approved general-purpose third-party OAuth integration. Recheck this guidance before broad distribution or changes to authentication/billing. The native command and account status interface are documented in the [CLI reference](https://code.claude.com/docs/en/cli-reference).

The bridge uses supported SDK queries, exact resolved model identifiers, SDK-hosted MCP tools for ADC outcomes, and only explicitly granted external MCP configurations. A required MCP startup failure blocks the turn before prompting the model. Native tools are an explicit list for ordinary work; proposal conversations have no native tools or external MCP grants. Provider-native agents, skills, plugins and discovered settings are omitted. These are tool exposure controls under the existing advisory host-access posture, not a claim that broad shell execution is sandboxed.

Runtime processes receive private account state and strip inherited Anthropic/Claude authentication and provider-selection overrides. SDK sessions are ephemeral; ADC owns documents, code/review bindings and recovery. Tool calls and results pass through the shared durable handlers. Cancellation interrupts the SDK query and the bridge closes native sessions on shutdown. Assistant usage updates are deduplicated by message ID in the bridge; cumulative per-model reports are normalized to the shared delta collector, including cache creation and unknown metrics. Final SDK model-usage totals also feed that collector; unavailable final callbacks remain possible after interruption. Reported usage is not a bill or subscription quota.

## Protected assignment mode

The ordinary/native configurations described above are the advisory path. Protected assignments instead expose only ADC-mediated workspace and connection tools. Copilot uses a separate empty-mode client; Codex has empty execution environments/runtime roots; direct Claude disables all native tools. The provider never receives configured external MCP credentials in this mode. Linux/Incus prerequisites, policy setup, qualifications and remaining authenticated repository limitations are documented in [Permissions](permissions.md). Existing assignments and approved schedules are not silently migrated.

## Self-hosted OpenAI-compatible provider

Connections → **+ Self-hosted** accepts an API base URL, an optional API key and a concurrency limit. A server URL without a path uses `/v1`; explicitly supplied paths such as `/api/v1` are preserved. The key is sealed in ADC's credential store, never put in model messages or worker files, and redirects are refused. HTTP and HTTPS follow the explicitly configured server transport; sealing at rest does not imply transport encryption. Only the owning human can inspect or edit the connection; active turns prevent endpoint/key replacement. Blank replacement keys retain the old key, with a separate explicit removal control. No hosted API billing or CLI credential import is involved.

The adapter uses the [OpenAI-compatible Chat Completions and model catalog](https://lemonade-server.ai/docs/api/openai/) interfaces. It discovers live model IDs and supplies ADC's existing function schemas. Models must have recognized family-identifying IDs; common GPT, Claude, Gemini, Grok, Qwen, DeepSeek, Llama, Gemma and Mistral identifiers are recognized, including namespace prefixes. An arbitrary alias is not accepted as proof of review independence. Capability labels are advisory: explicit non-chat modalities are excluded unless chat is also advertised; chat-only and vendor-specific labels are retained. Actual function-call qualification is still required. Different endpoints do not make the same model family independent.

Self-hosted non-proposal assignments currently require protected execution, reusing ADC's workspace/MCP gateway instead of introducing a broad shell or passing integration credentials to the model server. New self-hosted assignments with no explicit execution mode default to protected; explicitly advisory work is rejected with a concrete configuration message. Existing providers and assignments retain their settings. Roles and funding remain explicit: the current assignment portfolio supports one primary and one additional provider account belonging to the same human. Three-provider coordination needs a later portfolio extension; connecting another account does not silently fund it.

Each activation starts from durable ADC evidence, as the existing CLI adapters do. The in-memory provider conversation handles function calls and correlated tool results. Tool outcomes, documents, code, reviews, messages and traces persist in ADC. Interrupted inference never automatically replays a tool handler; recovery starts with current recorded evidence and reconciliation instructions. Cancellation and steering are checked between requests and before tool dispatch. A successful ADC outcome ends the loop immediately, and remaining calls in that response do not execute. Unknown tools and malformed JSON receive bounded errors for correction; truncated completions, duplicate tool IDs and differing response model IDs do not dispatch effects.

Usage is attributed to the selected personal account, run and model, retaining unknown metrics and deduplicating by activation/request. The first slice supports text and function calling through non-streaming HTTP responses; activity updates as messages/tool calls complete. It does not provide image input, audio, live token deltas, model installation/loading controls, or automatic alias-to-family assertions. Compatible-server response and inference limits still apply. Requests allow up to ten minutes within the existing activation deadline, and cancellation remains immediate; large local-model prompts may have substantial initial latency.

The full Qwen-supervisor prompt exceeded the initial three-minute client timeout before any ADC tool effect. The timeout was increased, and end-to-end qualification passed using a Claude supervisor, Qwen workers and independent Claude review in an isolated document fixture. Both dependent steps completed with passing reviews, no failed tools and no human continuation; readiness and usage attribution passed for all expected runs.
