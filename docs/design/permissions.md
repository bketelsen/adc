# Protected execution and permissions

Protected execution is an opt-in Linux assignment mode. Open Connections → Permissions to review discovered tools, set policies, and choose the default for new assignments. The assignment form can also select a mode explicitly. Existing assignments keep their mode. Approved schedules snapshot their mode and capability ceiling; changing an organization default does not migrate them. An empty historical mode means advisory. Advisory runs retain native host access and must not be described as sandboxed.

## Linux installation

Install the distribution's Bubblewrap, util-linux (`prlimit`), Bash, Python 3, Git, curl and CA certificates. The tested profile uses `/usr` as a read-only runtime, minimal networking/CA paths, private process visibility, a writable run workspace and persistent private HOME. It drops capabilities, blocks nested user namespaces and exposes no host home, ADC state, provider authentication, sibling workspace or agent sockets. ADC state must live outside all mounted runtime/networking paths; preflight rejects overlapping or symlink-relocated state.

An unprivileged Debian trixie Incus container passed the executor qualification as UID/GID 65534 with `security.nesting=true`. Without nesting, Bubblewrap could not mount private `/proc` and protected execution failed closed. Configure nesting on the ADC container explicitly; privileged containers are not required. No host-specific topology or maintenance coordination is built into ADC.

Ordinary outbound networking is allowed, including LAN access. ADC endpoints require human authentication and CSRF checks even on loopback. Network reachability is not authorization, and information legitimately available to a worker can leave over that network. Shared-kernel availability remains a limitation: commands have timeout, output, descriptor, CPU and individual-file limits, but no aggregate memory/process/disk quotas.

Provider integrations were exercised with Codex CLI 0.153.0, Copilot CLI 1.0.83 / Go SDK 1.0.8, and pinned Claude Agent SDK 0.3.268. Requalify provider upgrades that change tool exposure. Protected Codex threads have empty execution environments and runtime roots; Claude has no native tools; Copilot uses an empty client and source-qualified custom tool allowlist. Only ADC handlers can execute workspace commands or dispatch credentialed operations. Provider runtimes themselves remain trusted authenticated processes. Missing Linux prerequisites fail closed; ADC never retries a protected assignment with advisory access.

## Connection setup and grants

Discover an administrator-configured MCP connection once, then inspect its tool descriptions and schemas. Discovery starts the configured server but invokes no tool operations. The gateway supports stdio and Streamable HTTP; it does not expose MCP sampling, elicitation, roots, resources or prompts. HTTP redirects are rejected; sessions and results are bounded. Stdio starts with explicit environment, private HOME and process cleanup. Connection secrets remain in the trusted gateway and are redacted from returned evidence. Server binaries are trusted integrations, not sandboxed worker code.

Each tool has allow, require-approval or deny policy and an observation/change/broad classification. Annotations are suggestions, never authority. Bulk classification applies reviewed settings atomically to selected tools. Optional restrictions use JSON Pointer and finite allowed JSON values, for example `[{"Pointer":"/target","Allowed":["nas-one"]}]`. An empty restriction list permits all schema-valid arguments within the other applicable grants. General command/API tools remain broad capabilities regardless of their names.

Protected assignments snapshot standing grants only for connections held by the accountable agent. Each call must satisfy current connection membership, the current tool/configuration fingerprint, current policy and the assignment's grant ceiling. Delegation can remove connections but cannot regain them from a more powerful recipient. Later policy widening does not widen existing assignments; new denials or tighter restrictions apply to new dispatches immediately. Revocation epochs prevent old grants from reviving when a policy is re-enabled. Connection/schema/metadata changes invalidate the old fingerprint. Changed classification requires a corresponding fresh grant. Approving an access request cannot reclassify a stale existing tool policy or erase its installation restrictions; reclassification uses the versioned human policy form.

The first release has connection grants on roles and per-tool policy at organization/assignment level; it does not yet provide per-role tool rules, expiration dates or per-tool delegation forms.

## Missing access and recovery

Agents use `adc_request_access` to propose a purpose and one bundled list of capabilities. It pauses the requesting run and creates a shared human decision. Equivalent requests coalesce; other work keeps moving. The human can inspect exact proposed arguments, edit restrictions, and approve one operation, the assignment, or explicitly standing access. Supplied Arguments become a whole-object equality restriction, including absent optional keys. Agents proposing a variable capability must omit Arguments and show their finite Constraints explicitly; mismatched arguments and constraints are rejected. Editing restrictions creates a fresh revision and clears the old exact-operation selection. Stale forms cannot approve superseded requests. Approval extends only the requesting chain's connection access in that assignment; it does not edit permanent roles. Standing access affects future assignments that already hold that connection. Each approved standing rule is an alternative beneath the installation ceiling: approving target Y does not disable target X or expand an older assignment. The policy form displays these rules; saving a reviewed policy replaces them with the settings shown in that form.

Approval and outcome records persist in SQLite. A stable operation identity is scoped to the assignment and bound to exact canonical arguments and tool fingerprint. ADC records intent before dispatch. A completed retry returns the recorded result; an in-flight/uncertain result is not automatically replayed. It must be reconciled using a service's status/idempotency facilities, or reported as uncertain. Changing an operation ID is not reconciliation. Read classification does not yet enable automatic safe retries. Deny revokes all grants for new dispatch. Changing Allow to Require approval revokes grants inherited from standing policy; the approving assignment’s separately explicit grant remains until denied or invalidated. Revocation cannot undo or reliably cancel an already admitted remote effect. Cancelling an assignment also closes its pending permission decisions.

## Useful repository work and limits

`adc_workspace` supports public cloning, dependencies in the private HOME, editing, local commits and tests. Code registration and Git verification run inside the same sandbox. Reviewers use `adc_checkout_code` to obtain a committed snapshot in their own workspace; repository code and hooks never run in ADC's trusted process.

Protected work has no personal `gh` credential or authenticated Git helper. Private fetch, push and draft PR publication need an approved mediated MCP operation supplied by an integration; a general unrestricted GitHub API tool would still be broad authority. No built-in GitHub publication adapter or real protected publication has been qualified. Existing advisory repository workflows remain available explicitly. Selecting protected mode for an unsupported authenticated operation must yield a concrete missing capability, not an automatic downgrade.

Do not migrate working tool classifications by inference. Review the concrete policy on Connections → Permissions, then select protected execution for appropriate new work. Changing the default back to advisory affects new assignments only; active protected work retains its boundary.
