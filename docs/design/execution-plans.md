# Durable execution plans

An execution plan decomposes an existing assignment into bounded, named steps. It is source-linked workspace evidence, not new authority. The supervisor can save a draft for discussion and start it when execution is already authorized. Starting a plan never widens the assignment's authority, tool grants or subscription portfolio. Planning-only work should leave the plan in draft.

The first slice uses a directed acyclic graph within one assignment. Each step has a stable human-readable key, owner, reviewer from another model family, brief, completion criteria and prerequisite keys. Agents use `adc_plan` to create/revise a draft or start it. Existing drafts use optimistic revisions; activation freezes the definition. Humans can inspect and start a draft from the assignment page. Ordinary corrections use existing review/reassignment rather than a new approval round.

ADC dispatches each step at most once, atomically recording its run and mapping. It arranges independent review after the worker finishes, routes corrections through the existing lifecycle, and unlocks dependents only after a current passing review. Required connections and the assignment's selected portfolio are validated before activation and again at dispatch. Paused/cancelled assignments do not dispatch. Waiting releases model capacity. A blocked branch does not suppress eligible siblings. Supervisor completion includes every active plan step.

The live assignment view shows the source, revision, steps, owners, prerequisites, state, blocker, and run/review transcript links. Run and review evidence remains in existing ADC records. A draft neither runs nor blocks ordinary assignment completion. The first slice has one plan per assignment; an active definition cannot be silently replaced. Source descriptions are evidence, not instructions that override the original assignment.

Steps without explicit requirements retain reviewed ADC work as their completion gate. Steps can now declare typed milestone requirements as described below. Durable read-only observation and timer waits are described below. Repository/integration provenance is described below; step-bound operational approvals and mediated delivery remain EP5–EP6. Core Plan 0007 is a design/qualification example; this feature does not execute its production migration.

Activation freezes role/model selections and step definitions. Dispatch rechecks current role availability, narrower authority/tool grants and the funded portfolio. Missing prerequisites or access appear as blockers for supervision. If a prerequisite’s recorded evidence changes after a dependent starts, further queued dispatch/completion is held until that prerequisite has a fresh designated-reviewer pass. Once old worker/review attempts and their children have yielded, ADC preserves them as superseded history and schedules a fresh attempt against the new evidence. The new worker must inspect prior artifacts and reconcile any external effects before repeating actions. This does not undo or preempt an already-running external action. Richer repository integration revalidation remains EP4. New step dispatch stops when the root is blocked/cancelled/complete or awaiting a human decision; step-specific decisions hold only their dependent branch. Active graphs cannot yet add/remove steps; use a separately scoped assignment for changed work rather than silently replacing the graph. Cancelling the assignment cancels its runs through the existing lifecycle.

## Explicit milestone requirements

Each step may declare up to 12 `Requirements`, with a unique `Key`, `Kind`, exact `Target` and concrete `Criteria`. All requirements must be satisfied alongside the step's designated independent review before dependents unlock. Separate steps allow reviewed code, a later merge, a released artifact and its canary observation to gate different branches. Plans remain general-purpose: target/reference strings identify the relevant artifact or environment without requiring a built-in GitHub or TrueNAS client.

| Kind | Required evidence |
| --- | --- |
| `reviewed-code` | Committed code registered through `adc_code`, existing code verification, and independent review against the target/criteria. |
| `merged-pr` | A worker observation of the exact merged change, with source reference and observation time, independently reviewed. |
| `published-release` | A worker observation of the exact published artifact/version, with source reference and observation time, independently reviewed. |
| `verified-canary` | A worker observation of the specified canary and acceptance checks, with source reference and observation time, independently reviewed. |
| `human-evidence` | An authenticated organization member's observation and source reference, then independent review against the criteria. Agents cannot submit it. |

The current planned worker uses `adc_milestone` with `Requirement`, matching `Kind` and `Target`, `Summary`, `Reference`, RFC3339 `ObservedAt`, and optimistic evidence `Revision` (0 initially). `adc_status` exposes the plan and current evidence. Neither a generic completion message nor a review of code can fill an absent external observation. Missing required evidence prevents worker completion and review PASS. Reviewers must independently inspect the observation's substance, artifact identity and source; a source URL or type label alone is insufficient verification.

Humans enter attestations in the step's **Required milestones** disclosure on the assignment page. All organization members have equal authority. This records evidence, not permission to perform the operation described by it. A worker awaiting human evidence uses `adc_wait`, freeing its slot until input arrives. A frozen `Wait` can collect external evidence or elapsed-time evidence automatically, as described below. Workers without an automatic wait or a real external result must report the blocker rather than invent completion or poll continuously.

Evidence is bound to the plan's current worker attempt and included in its review revision. Replacements and withdrawals retain historical records and invalidate current review and dependent input pins. Human changes wake yielded workers, arrange fresh review, and reopen an already-ready assignment atomically. Old dependent attempts retire only after they have yielded, using the existing recovery rules. Prior external effects are never undone or blindly repeated. Human evidence for a superseded attempt cannot be reused as a new attestation automatically. Stale forms and tool writes are rejected; live UI updates preserve unsaved input and its original evidence revision.

These external packets are **agent-reported observations checked by an independent model**, or explicitly human-supplied evidence. Requirements with `Wait` use ADC-collected observations instead, as described below. ADC does not cryptographically attest upstream responses or record every validation command/environment as structured check results. Richer integration and validation evidence remain EP4 and the validation refinements backlog. Existing authority, capability grants and publication boundaries continue to apply.

## Durable external and timed waits (EP3)

A requirement may carry a frozen `Wait` definition. Its worker registers it using `adc_await` and yields with `adc_wait`. ADC stores the observer, next check, deadline, generation, last result, observed version and matching interval in SQLite. Background reads have a separate limit of four concurrent calls across the installation; they do not consume model subscriptions or worker slots. Only the relevant owner resumes on satisfaction or failure, and independent step review still gates dependents. The supervisor's existing plan waits keep unaffected branches moving.

An external wait uses an already-discovered MCP tool. It declares the exact tool ID, `Arguments` as a JSON object string, `Match` entries with JSON `Pointer` and `ExpectedJSON`, a `VersionPointer`, `StableSeconds`, `PollSeconds` (30 seconds to one day), and `TimeoutSeconds` (greater than the stable period, at most 366 days). The tool must return `structuredContent` or one text block containing valid JSON. All predicates must match; a nonempty string/number version identity is required. Failed conditions, tool errors, and version changes reset the matching interval. Optional `EventTimePointer` requires an RFC3339 event timestamp at or after the first registration and no later than the check. That event boundary survives retries, so a previously observed publication does not require another publication just to recover monitoring.

For a 48-hour publication observation, choose the exact producer/artifact target in the tool arguments and predicates, a release/commit identity as `VersionPointer`, the publication timestamp as `EventTimePointer` if it must occur after registration, and `StableSeconds: 172800`. The gate requires a fresh matching observation after that duration; elapsed time alone cannot satisfy it. A timer-only requirement uses kind `elapsed-time` with a positive `StableSeconds` and timeout, without a tool or predicates. Timer duration begins on registration, never at a model-supplied backdated timestamp. On a late restart, ADC records an already-elapsed timer rather than restarting its clock; the external-observation deadline cannot undo elapsed wall time.

The gateway rechecks current read classification, connection/configuration fingerprint, current role and run connection grants, and argument limits before opening a connection and immediately before dispatch. Protected workers additionally need an existing reusable assignment capability; one-shot operation grants cannot authorize repeated polls. Advisory workers need explicit allow/read installation policy and matching standing constraints. No background shell commands, model turns or credential access are introduced. This relies on the human's classification and the trusted MCP server behaving as a read-only integration; metadata hints alone are not permission.

Claims have a persisted 90-second lease and generation. After interruption, ADC waits for the lease to expire and obtains a fresh read, safely repeating only the permitted read. Duplicate or late results cannot record a second milestone or satisfy a newer generation. Observation completion, the milestone packet and owner wake commit together. New source or permission failures stay visible; external polls stop at the deadline. The owner can retry a failed wait after addressing its cause, retaining the previous generation as history. A retry restarts the elapsed matching period and deadline, while preserving the original event boundary and frozen conditions. It cannot change target, predicate, tool or authority. A definition error in an active plan needs newly scoped work, consistent with immutable activated graphs.

Paused/cancelled assignments and superseded attempts do not dispatch observations; late results cannot complete them. Explicit pauses reset external matching intervals. Timer-only waits measure wall time and remain held until the assignment resumes. Pending human decisions remain pending when an observation arrives. The plan's milestone disclosure shows the wait state, deadline, last/next check, current reason and saved redacted result. An ordinary unchanged poll does not generate a model activation or a stream of activity messages.

This is sampled observation, not uninterrupted monitoring: downtime or gaps between polls are not proof that a condition held continuously. Completion requires the same observed version in a fresh matching sample; an external failure or changed version resets the interval when observed. Completed waits retain their point-in-time evidence and stop polling. They do not automatically revoke completed work when an external resource later changes. Webhooks, dedicated GitHub adapters, full observation histories and continuous-health guarantees are outside this slice; integration revalidation remains EP4.


## Repository and integration evidence (EP4)

A step can freeze required `Repositories` (canonical identity references) and `Checks` with a unique `Key`, `Kind` (`command`, `integration`, or `visual`), concrete `Verifier` and acceptance `Criteria`. A command verifier is its exact shell command. `Observed: true` requires a protected assignment; it cannot be satisfied by a model's report. Existing steps without these declarations retain their original gates.

The worker registers its clean committed repositories with `adc_code`, then records `adc_integration` with each repository's identity, registered path and output commit, exact ancestor base commit, and optional PR/release references. ADC verifies the base/output relationship in the existing worker execution boundary. `Consumes` names direct prerequisite steps, repository identities and exact output commits; mismatches are rejected. An integration check requires every repository output on its direct prerequisite edges to appear in this tested combination. `Environment` records named version pins for tools, datasets and external dependencies. Updates use optimistic revisions and preserve historical evidence.

`adc_status` exposes the artifact pin and current ledger revision. Once artifacts and environment are ready, `adc_check` records a result against those pins, including verifier, outcome, supporting output and optional references. These results are explicitly **agent-reported**. Protected workers can use `adc_validate` to execute a frozen command, with ADC recording its actual exit/output as **adc-command** evidence. Commands are bounded to 300 seconds and are never automatically retried. They run with the existing protected workspace and ordinary outbound networking; this tool does not add external credentials or action authority.

Missing, failed, inapplicable, stale or insufficiently observed required checks prevent completion and review PASS. Inapplicable is an inspectable blocker, not a waiver. Final code/documents, milestone observations, environment, consumed versions and frozen prerequisite input pins determine the artifact revision. Changing those invalidates the applicable checks; recording check results or the final completion message does not invalidate its own artifact pin. Check results and their history are included in the independent-review revision. The existing graph retires affected downstream attempts after input changes, preserving unrelated branches and earlier evidence. Overlapping repository work still uses isolated workspaces rather than an organization-wide repository lock.

Reviewers receive an explicit `review_brief` in status: the original request and authority, step criteria, authoritative source references, exact revision, code/documents, tested combination and check results. The brief asks them to assess unrelated changes, disabled/weakened checks and unmet criteria even when deterministic checks pass. This uses the existing independent reviewer; it does not introduce another agent tier.

Visual checks can retain workspace screenshot/interaction references and supporting results under the same revision gate. Their criteria should specify affected flows, desktop/phone coverage, browser errors and comparable baseline availability. References and agent-reported results require independent inspection. ADC does not yet capture screenshots itself or verify that a reference actually contains the claimed image. Evidence is not published merely by recording it.

Limits: repository identities, PR/release references, environment versions and claimed consumed versions remain worker declarations for independent verification. ADC verifies local commits and declared dependency equality, not remote repository ownership or the runtime's actual loaded dependencies. `adc_validate` observes a command's exit/output, not the quality of its assertions. Protected execution is required for ADC-observed commands; advisory workers can record reports. Check definitions stay immutable during an active plan; a genuinely inapplicable requirement needs supervisor reassessment or newly scoped work. Operational approval binding and credential-mediated GitHub delivery are EP5 and EP6.


## Step-bound operational approvals (EP5)

Protected MCP calls to change/broad tools in an active execution plan require an exact operational approval, even when the assignment holds a broader standing capability. Read-classified tools and ordinary workspace checks/corrections keep their existing grants. This boundary is enforced in the gateway; advisory execution retains its previously documented limits.

The current planned worker uses the existing `adc_request_access` bundle. Each proposed operation supplies exact `Arguments`, a stable `Operation` identifier and `Context` containing `Action`, `Target`, `Environment`, expected `Effect`, `Validation` and `Rollback` (or a concrete stop/recovery plan). ADC supplies the plan revision, step/attempt, artifact revision and full evidence revision. Models cannot choose those binding fields. Humans see the context, canonical arguments and pins together with a link to the assignment's evidence; they may approve the exact operation or decline. A bound proposal cannot be promoted to assignment/standing access or lose its exact arguments through the generic constraint editor. Discuss a changed action with the worker for a revised concrete proposal.

Approval checks the current binding again. Gateway admission checks it once more immediately before dispatch, including current local code and prerequisite evidence. A changed artifact, check result, dependency, plan revision or attempt requires fresh approval. A worker can refresh a stale pending proposal for the same run/tool/operation without leaving the old stale entry in its bundle; history and optimistic decision revisions are retained. The existing durable operation journal returns a completed result when the exact operation is replayed; uncertain outcomes still require reconciliation. A different operation ID, target arguments, sibling, root or delegated child cannot borrow that one operation's approval.

This does not interpret arbitrary API arguments semantically. The action/target/environment description is a proposal; the human must inspect its canonical arguments. ADC can enforce exact identity, version and argument equality without needing a custom policy engine for each MCP server. Observation/validation records do not themselves grant execution authority. The approval UI records the decision and resumes the worker; it does not execute the operation in the browser request.


A bundle containing both bound operations and unbound reads presents an explicit combined decision: **these exact operations and the listed read access for this assignment**. Only human-classified read entries receive reusable assignment grants; each mutation keeps its one-operation binding. Choosing ordinary operation-only scope never silently creates reusable read access. Bound bundles from different owners remain separate, so stale evidence on one branch cannot trap another branch's request. The scheduler expires stale bound proposals atomically, preserves them and their decisions in history, and resumes the current yielded owner to correct/re-propose unless another human question is pending. Expiration grants nothing.

After all steps finish, the actual accountable supervisor can propose a finalization operation bound to the complete graph's current reviewed evidence. Finishing a plan never re-enables unbound mutation grants. Changed step evidence invalidates the finalization binding as well. Reviewers and delegated children cannot manufacture a step-owner binding.

## Execution readiness and mediated repository delivery (EP6)

`Preflight` and `ReviewPreflight` are optional step declarations; ordinary delegation also accepts `Preflight`. They name known prerequisites without requiring a prediction of every permission or tool a task will need:

```json
{
  "Models": true,
  "Commands": ["git", "python3"],
  "Repositories": [{"Connection": "configured-github-connection-id", "Owner": "example", "Repository": "project", "Write": true}],
  "Directories": ["test-data"],
  "Ports": ["test-http"]
}
```

ADC checks executable presence in the actual protected worker environment, repository identity/reported token access through the read-only gateway, and live provider model availability in the assignment owner's funded portfolio. `Models: true` also checks the designated planned reviewer before starting the author; review dispatch checks that model again. Runtime version compatibility and test assertion quality remain validation criteria, and repository metadata is not proof that every branch rule or token permission will allow a future write. Checks never perform a repository write to test access.

At most four asynchronous preflight probes run independently of model slots. Persisted generations and leases recover interrupted checks, and configuration changes invalidate in-flight results. Blockers retry after a minute; changed configuration can trigger a fresh check sooner. These checks do not create human approval requests or model polling loops. The execution-plan disclosure and `adc_status` show the individual observations. Required connection declarations and normal permission checks continue to apply at handoff and operation dispatch.

Protected runs can request named test directories and local port suggestions. `adc_status.resources` records the owner, paths and port values; each run has its own workspace and test data. Port suggestions are coordinated among ADC runs, **not exclusive reservations against other host processes**. Applications must still handle bind failure. ADC releases its port coordination records after task completion/cancellation or a cancelled/superseded run has stopped. Workspace files and durable evidence remain available for review; this slice does not implement automatic file garbage collection or remote environment provisioning. Resources never grant additional filesystem or network access.

The built-in GitHub connection adds `github_repository`, `github_pull_request`, `github_release`, `github_checks`, `github_fetch` and `github_draft_pr` to the existing catalog. Configure a sealed token and explicit `owner/repository` scopes (or an intentional `owner/*` scope) in Connections, then discover/classify tools in Permissions and grant the connection to the relevant roles. Read tools can also back existing durable milestone waits. CI observations aggregate at most 1,000 check runs and reject incomplete results; they do not claim to cover separate legacy commit-status contexts or deployment checks.

Authenticated fetch occurs in a trusted temporary bare Git repository, then imports a credential-free bundle into the calling protected worker. The result identifies the repository, exact commit and original import path. Replaying a fetch returns that path; it does not recreate deleted files or return another worker's workspace.

Draft delivery requires explicit assignment publication authorization, current independent review and all applicable gates on the exact registered source commit. For a planned operation, EP5's artifact-bound approval remains required. ADC exports the source through the protected boundary, rechecks the current base and remote branch, and pushes to a deterministic ADC branch with an expected-head lease and ancestry checks. It rejects changed/deleted external heads and closed/promoted pull requests. Policy, source and review are rechecked before remote mutations. There is no merge, release-publication or deployment tool.

A durable delivery record reconciles its existing branch and draft after an interrupted response, including across restart, instead of creating another PR. Known failures before any mutation are labelled failed; attempted effects with no confirmed outcome are uncertain. Both can be retried with the same operation identifier in this narrow adapter after resolving the cause; arguments remain pinned and a reviewed change needs a new concrete operation proposal. Generic MCP uncertain mutations still require service-specific reconciliation. New source runs have distinct delivery branches; this implementation does not automatically consolidate or close earlier drafts.

Qualification uses actual protected Git operations against explicitly synthetic local bare repositories and authenticated HTTP fixtures. No real GitHub PR was published to qualify this feature. Live provider qualification separately exercises Codex execution, automatic preflight and independent Claude review.
